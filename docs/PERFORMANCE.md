# 性能优化验证

## 2026-10-08：全尺寸花纹采样优化

花纹放大到打印分辨率时，多行输出会使用相同的两行原素材。现在每个渲染块仅对实际使用的源行计算一次横向插值，再进行纵向插值，并复用私有临时数组。曲线边框等非网格坐标仍采用四邻点采样；不适合复用的网格回退原计算路径。

使用 `benchmarks/export_performance.py` 的固定合成素材，在同一个 Python 进程中先使用修改前的采样函数、再使用优化后的函数测量。参数为弧形台 151×91cm、直边 120.5cm、150 DPI，画布共 47,919,958 像素；素材在内存中准备完成，输出到本地临时目录。

| 阶段 | 修改前 | 修改后 |
|---|---:|---:|
| 渲染 | 25.25s | 18.80s |
| JPG 编码保存 | 0.82s | 0.74s |
| PNG 编码保存 | 2.76s | 3.21s |
| 渲染 + JPG 编码保存 | 26.07s | 19.54s |

本次对比中，渲染耗时减少约 26%，渲染加 JPG 保存的耗时减少约 25%。优化针对采样，编码参数保持不变；PNG 编码没有提速承诺。可运行 `python -B benchmarks/export_performance.py` 测量当前版本。

**重要说明：**

- 桌面“成品已保存”旁的“用时”是完整生成过程，包含匹配、素材读取与分析、渲染、编码和保存。鼠标停在状态文字上可以查看分阶段耗时，不能将总耗时直接视为纯保存耗时。
- 上表仅包含渲染和编码保存，不含素材首次读取、分析及图库匹配；本地合成素材不代表真实共享图库的固定速度。实际提速受素材分辨率、缩放比例、尺寸、DPI、图片内容、硬件负载与网络读写影响。
- 本轮保持导出 DPI、尺寸、花纹映射、透明通道和 JPG/PNG 编码参数；与上一版 float32 插值算法逐像素一致。前期由 float64 改为 float32 的允许误差记录仍见下方历史验证。
- 重启应用后使用更新后的代码。缓存只在进程内保留，重启后首次素材读取和匹配仍有额外成本。

验证命令：`python -B -m pytest tests -q -p no:cacheprovider`，完整测试结果 **198 passed**。新增检查覆盖 RGB/RGBA、平铺和截边、反向坐标、单行/单列与缩小采样，并通过源像素读取计数验证放大采样复用源行。

## 历史验证：缓存、float32 采样与编码

使用同一工作区 `.venv\Scripts\python.exe benchmarks/performance.py` 在修改前后测量。
测试为临时图库 6000 个 JPG 文件名、30 个花型；素材为固定随机种子的 1600×900 RGB PNG，
成品参数为 140×78cm、40 DPI（2205×1228px）。重复匹配取 12 次平均，素材准备和编码取 3 次平均。

| 阶段 | 修改前 | 修改后 | 对比 |
|---|---:|---:|---:|
| 首次匹配 | 20.2ms | 71.9ms | 首次解析所有花型并建立索引，有额外成本 |
| 重复匹配 | 23.2ms | 3.8ms | 约 6.1 倍速度 |
| 重复素材准备 | 146.9ms | 0.1ms | 复用读取和边框分析结果 |
| 生成成品画布（素材已使用过） | 1122ms | 426.7ms | 约 2.6 倍速度 |
| PNG 编码保存 | 361.3ms | 161.7ms | 约 2.2 倍速度 |
| JPG 编码保存 | 51.3ms | 35.8ms | 编码质量保持不变，绝对差异较小 |

这些是本地合成基准，不代表所有真实素材的固定速度；PNG 压缩收益与图像内容有关。
首次扫描、素材首次读取、大幅高 DPI 画布仍有成本。索引和素材缓存仅在程序运行期间保留。
PNG 采用较低压缩级别，像素和透明度保持无损，但文件可能更大。
插值改为 float32，随机采样与旧实现比较的通道差不超过 1 个灰度级。

匹配优化复用花型解析及分组，仍核对目录条目。不能只靠目录时间戳：测试发现 NTFS
会延迟反映快速删除；已验证连续新增、删除、改名以及新增子目录都能刷新匹配结果。
素材缓存按文件标识、修改时间、大小及参数失效，限制为 8 项 / 256MiB，只读数组防止污染。

验证命令：`python -m pytest tests -q --tb=short`，结果 **84 passed**。
覆盖后台预览到 JPG 导出、PNG 像素/DPI、旧输出原子保护、进度完成时机、
图库变更、素材替换、采样精度，以及现有几何、边框、花纹保真与布局回归。

界面检查：`python benchmarks/gui_preview.py` 生成 `outputs/gui-preview.png`、
`outputs/gui-empty.png`、`outputs/gui-compact.png`，检查 1280×850 与 1000×720 的布局。

## 22 万张网络图库：连续换订单回归

上一轮合成基准没有覆盖不同花型的首次大图读取，也低估了 SMB 目录枚举。
针对用户提供的 221905 张、持续增长的共享图库，只读抽取两个不同花型并实测：

| 阶段 | 每次核对目录 | 桌面递归监听索引 |
|---|---:|---:|
| 首次建立索引并匹配 | 23.597s | 21.839s |
| 第二种花型匹配 | 17.420s | 0.011s |
| 第二种花型预览 | 0.353s | 0.332s |
| 第二单匹配 + 预览 | 17.773s | 0.343s |

两个抽样原图分别为 7087×2209（4.4MB）、9685×2067（4.7MB）。预览数据包含此次新增的
缩图路径；目录模式对比两次采用相同版本。监听在真实共享盘成功启动，不修改共享文件。
运行 `python benchmarks/catalog_probe.py "图库路径" --session` 可复测。

首次匹配仍需一次全库扫描，索引仅保留在进程中；重启或监听失效后的核对仍有网络成本。
Windows 监听按条目通知做增量更新，正常换单不再枚举目录。文件新增/删除/改名、子目录新增、
手动刷新、监听回退、监听关闭、不同订单预览与原分辨率导出均有回归测试。
桌面状态栏显示每次匹配和预览的秒数，避免将网络扫描时间与图片处理混为一谈。

最终完整检查 `python -m pytest tests -q --tb=short`：**91 passed**，包括桌面后台
“第一单导出到图库所在目录 → 更换另一花型 → 生成预览”，断言第二单不调用目录枚举。
GUI 测试设置保存到测试临时 INI，避免覆盖用户已选择的图库和输出目录。
本机诊断与测试进程设置 `OPENBLAS_NUM_THREADS=1`，避免诊断环境数值库线程初始化的内存开销；
产品匹配、图像采样不依赖 BLAS 矩阵运算。
